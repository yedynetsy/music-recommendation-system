# Music Recommendation System

The backend is a FastAPI catalog and token-authentication API backed by
SQLAlchemy and Alembic. The framework-independent `recommendations` package
contains offline experiments and the model used for new-user inference.

## Project structure

- `backend/`: FastAPI routes, SQLAlchemy models, and application services.
- `recommendations/`: framework-independent data preparation, ALS, evaluation,
  artifact serialization, and inference.
- `demo/`: Streamlit interface and its HTTP API client.
- `scripts/`: command-line entry points for data and account setup.
- `tests/`: backend, recommendation, and demo tests with shared fixtures.
- `migrations/`: Alembic schema history.
- `docs/`: [architecture](docs/architecture.md) and
  [evaluation details](docs/evaluation.md).

## Backend setup

For PostgreSQL with a containerized API and demo, see
[Docker Compose setup](docs/containers.md). The local setup below uses SQLite
unless configured otherwise.

Install the project, then create a fresh database from the repository root:

```sh
python -m pip install -e .
python -m alembic upgrade head
python -m scripts.create_staff
python -m uvicorn backend.main:app --port 8001
```

The default URL is `sqlite:///db.sqlite3` in the repository root. Set
`MUSIC_DATABASE_URL` for another SQLite database or PostgreSQL; both Alembic
and the API use it. The app never creates tables automatically. The initial
Alembic revision creates users, tokens, artists, and albums; the second adds
tracks, app listens, and recommendation exposures. The first revision retains
the old table names so existing local catalog data and PBKDF2-SHA256 password
hashes remain readable. The password verifier supports that hash format;
accounts using a different legacy hash algorithm require a password reset.

An existing database created by the previous backend already has the first
revision's tables. Back it up and inspect its schema, then run
`python -m alembic stamp 0001_catalog_schema` once and
`python -m alembic upgrade head`. The stamp records the existing baseline;
the upgrade creates the new tables. A database already stamped at the first
revision only needs `upgrade head`. The third revision stores artist choices
and indexes catalog artist MBIDs. Local `db.sqlite3` files and backups stay
outside Git. The legacy database still has unused Django support tables and
indexes; `alembic check` reports them as schema differences. Do not apply
autogenerated drops without reviewing them. A fresh database has no such
differences.

## Catalog and authentication

`POST /api/user/register/` creates a user and returns a token (`201`).
`POST /api/user/login/` returns a token for valid credentials (`200`), reusing
an existing token. `POST /api/user/logout/` revokes that token (`204`). These
routes accept JSON request bodies. Registering creates a regular user; catalog
writes require a staff account. No public endpoint grants staff access.
The local `create_staff` command prompts for a username and hidden password;
run it after the migration to create the first staff account.

`GET /api/artists/` lists artists by name. `GET /api/artists/{id}/` returns one
artist or `404`. Both routes are public. `POST /api/artists/` and `PUT`, `PATCH`,
and `DELETE /api/artists/{id}/` require an active staff user's token in the
`Authorization: Token <key>` header.
Invalid artist input returns `400`; deleting an artist with albums returns
`409` and keeps the artist.

`GET /api/albums/` lists albums by name and `GET /api/albums/{id}/` returns an
album with both `artist` (ID) and `artist_detail` (artist object). Both are
public. `POST /api/albums/` and `PUT`, `PATCH`, and `DELETE` on
`/api/albums/{id}/` require an active staff user's token. Creating an album
requires a name and an existing artist ID; description and release date are
optional. Invalid input or an unknown artist returns `400`, and an unknown
album returns `404`. Updates retain optional fields when omitted; send
`release_date: null` to clear a date. PostgreSQL integration checks and their
opt-in command are documented in [containers.md](docs/containers.md#verify).

## Track catalog and recommendations

The track catalog uses canonical track MusicBrainz IDs as keys.
`GET /api/tracks/` is public, paginated (`limit` up to 100, `offset`) and accepts
an optional `query` for track or artist names. `GET /api/tracks/{mbid}/`
returns one track or `404`. Duplicate names remain separate records. Track
metadata comes from the first selected **pre-cutoff** event for each MBID;
missing names are nullable. Historical artist names and MBIDs are descriptive
metadata and are not joined to the separate application artist table by name.

After creating or upgrading the database, build the model artifact and import
the matching pre-cutoff track catalog from the same sample and cutoff:

```sh
OPENBLAS_NUM_THREADS=1 python -m scripts.export_model \
  data/sample-bucket-0-of-10.tsv data/als-model.npz \
  --cutoff 2009-01-01T00:00:00Z
python -m scripts.import_catalog data/sample-bucket-0-of-10.tsv \
  --cutoff 2009-01-01T00:00:00Z
```

`data/als-model.npz` is the default artifact path; `MUSIC_MODEL_PATH` can
override it. The artifact contains item factors, ordered MBIDs, popularity,
cutoff and source checksum, but no Last.fm user IDs. Its model version also
depends on the saved factor values. Keep it and the source
sample out of Git. Restart the API after replacing an artifact so its cached
model is reloaded. Import is idempotent and does not overwrite existing
metadata. If the model is missing or recommended MBIDs are absent from the
catalog, the recommendation route returns `503`.

Authenticated application users can record a new listening event with
`POST /api/tracks/{mbid}/listens/`. `GET /api/recommendations/?limit=10`
returns up to 50 tracks, a `source` (`als`, `onboarding`, or `popularity`), and
the artifact's model version. A user with no listened MBIDs in the model and
no usable artist choices receives the popularity fallback. Otherwise, the API
solves a new user factor from app listens or artist seeds and the fixed item
factors. It filters the input tracks from the ranking and logs every returned
track as a recommendation exposure. No API
request retrains the full model. App listens and exposures are separate from
historical Last.fm events. `GET /api/onboarding/artists/search/?query=...`
searches the pre-cutoff track catalog and returns artist MusicBrainz IDs with
display names. It is public; names are never used as identifiers. Authenticated
users can read their saved choices with `GET /api/onboarding/artists/` and replace
them with `PUT /api/onboarding/artists/` and a JSON body such as
`{"artist_mbids": ["aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa"]}`. The list can
contain up to 10 distinct IDs present in the catalog; an empty list clears it.
When a user has no app listens known to the model, up to three model-known
tracks with the highest training popularity per selected artist seed an ALS
profile. These seeds are not recorded as listens. If the chosen artists have
no model-known tracks, the response uses popularity. Once the user has known
app listens, those take precedence over onboarding choices. Neither onboarding
nor new-user inference was measured by the offline warm-user evaluation.
`GET /api/tracks/{mbid}/similar/?limit=10` returns up to 50 model-known tracks
ranked by cosine similarity of ALS item factors. It requires a user token so
returned tracks can be logged as exposures with `source: "similar"`. The seed
track is excluded; duplicate names remain distinct MBIDs. A catalog track
absent from the model returns `404`, and a missing recommended catalog row
returns `503`. This is item-factor similarity, not a claim about audio or
semantic similarity, and it has not been separately evaluated.

A full local flow with the 254,730-track
sample, a temporary SQLite database, registration, fallback, ALS inference,
and exposure logging
peaked at about 294 MB of resident memory on the development Mac; this is a
measurement of that run, not a general capacity estimate.

## Last.fm 1K development sample

Obtain `lastfm-dataset-1K.tar.gz` from the [dataset record](https://zenodo.org/records/6090214)
and extract `userid-timestamp-artid-artname-traid-traname.tsv` locally. Do not
commit the source file, sample, or model outputs. The dataset is available for
non-commercial use and requires a reference to [Last.fm](https://www.last.fm/).

```sh
python -m scripts.prepare_sample \
  data/lastfm-1k/userid-timestamp-artid-artname-traid-traname.tsv \
  data/sample.tsv --bucket-count 100 --bucket 0
```

The command streams the six-column TSV, selects complete user histories by a
stable SHA-256 bucket, retains track MusicBrainz IDs as keys, and prints event
counts. The default selects roughly 1% of users, but the actual size depends
on their listening activity. Rows without a track MusicBrainz ID are dropped
and counted; matching names would conflate different recordings. Artist and
track names remain descriptive metadata, not identifiers. No albums, explicit
likes/dislikes, or audio features are available as training signals here.

## Evaluation

The [evaluation protocol and measured results](docs/evaluation.md) describe the
shared temporal split, candidate policy, Recall@K, NDCG@K, reproducibility
commands, and the observed popularity/ALS comparison. The absolute scores are
low and do not establish online recommendation quality.

## Streamlit demo

Install the optional UI dependencies, then run the API and demo in separate
terminals from the repository root:

```sh
python -m pip install -e '.[demo]'
python -m uvicorn backend.main:app --port 8001
python -m streamlit run demo/app.py --server.address 127.0.0.1
```

The demo opens at `http://127.0.0.1:8501` and calls the API at
`http://127.0.0.1:8001` by default. Set `MUSIC_API_URL` or change the address
in the sidebar. Sign in or create a regular account, select artists by
MusicBrainz ID, request recommendations, search the catalog, record listens,
and inspect similar tracks. The API needs a migrated database, imported
pre-cutoff catalog, and matching model artifact as described above. Tokens are
kept in the Streamlit session for the local demo; use only on a trusted machine.
The UI does not retrain the model. Its results are not a live quality measure.

## Tests

All tests live in `tests/backend/`, `tests/recommendations/`, and `tests/demo/`.
Shared fixtures live in `tests/conftest.py`. The `recommendations/` package contains only
framework-independent ML logic; runnable data and setup commands live in
`scripts/`.

```sh
python -m pip install -e '.[dev]'
python -m pytest
```
